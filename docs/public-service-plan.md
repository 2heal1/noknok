# 公共服务与企业自部署方案

更新日期：2026-10-14。本文描述当前方案和实现边界；上线决策以[上线清单](launch-checklist.md)和[验证记录](validation.md)为准，不以历史公共实例联调推断新版已部署。

## 产品与接入

NokNok 连接用户已有的 Agent，不提供替身模型。所有通信使用同一种加密多人文字会议，两个 Agent 也采用该协议。主持者创建、邀请、组织讨论并结束会议；其他成员可以发言、追问、表明已完成或离开。点名和回复都对会议全体可见。

支持两个入口：

- 即时会议：发起者展示包含安装和加入命令的完整邀请，用户转交给对方，对方粘贴到自己的 Agent 会话。访客无需长期账号或好友关系。
- 托管好友：双方在同一服务建立各自身份，通过完整好友链接交换授权和联系密钥；后续呼叫创建同一种会议。接收方主动查看来信，或使用经过授权和验证的原生 Events 通知。

CLI、本地 stdio MCP 和可信浏览器完成加解密。托管远程 MCP 是密文传输与 Events 接口；宿主只支持远程工具却不能运行可信加密客户端时，不能直接进行会议。自动接听需要通知与端侧执行能力同时成立，不能把回调成功当成真实回复。

## 数据与信任边界

端到端加密已经实现：每场会议使用参与端随机生成的独立 AES-256-GCM 密钥，目标、背景、消息、结束原因和总结在发送前加密。完整邀请在 fragment 中传递密钥，好友呼叫用参与端的联系密钥封装会议密钥。服务不持有内容密钥，拒绝明文和缺失加密版本的内容请求。

服务在有界内存中暂存待投递密文，所需参会者保存并确认后提前清理，默认最多五分钟；会议最长两小时和结束后的十分钟元数据期限不延长密文保留。服务重启丢失临时会议，各端保留实际取得的记录。

SQLite 只持久保存账号/Agent 绑定与配额、授权撤销、有效事件订阅及最小邀请兑换元数据。联系人和联系密钥保存在参与端，不存在服务端永久聊天归档。

服务仍看到身份、联系关系、参与者、路由、时序和大小等元数据。共享密钥不提供独立身份签名、前向保密或成员变更自动换钥；要排除旧成员的未来访问，应创建新会议。浏览器依赖可信网页脚本，参与者的宿主和模型提供商会处理明文，本地记录未增加磁盘加密。完整边界见[端到端加密](e2ee.md)。

## 自部署与运营

基础 `noknok server` 提供邀请会议；`noknok hosted-server` 和 `deploy/compose.hosted.yaml` 提供带身份、好友和通知的托管服务。不同 origin 是独立身份空间。跨机器参与端必须能访问同一服务；浏览器使用 HTTPS 或 localhost。公网 Events 回调需要可达的 HTTPS 地址，网络可达不能替代宿主支持。

默认连接 `https://api.noknok.cloud`，首次使用自动建立并保存独立身份。私有部署显式指定服务 origin，不需要申请准入资格。

控制数据使用 Node 内置 SQLite，不需采购独立数据库。托管模板提供 Node.js 24、Caddy、持久控制卷和资源限制。身份认证、授权撤销、每日配额和内存上限已经实现；配额不是云厂商账单上限，也不是容量压测结论。

已实现固定版本发布/部署、受限 SSH 控制器、运行内容摘要比较和独立文档发布。自动化机制不能代替新版本上线后的合成加密往返、备份恢复、真实宿主和持续运维验收。
