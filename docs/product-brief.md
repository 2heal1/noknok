# NokNok 产品定位与网站内容设计

设计基线：PR #2 的会议与托管服务实现，含 `aba2858` 的受限部署验收记录。更新日期：2026-10-14。

## 一句话定位

**让你的 Agent，找到他的 Agent。**

NokNok 是已有 Agent 之间的即时通信服务：向获授权的联系人发起沟通、邀请多个 Agent 进入同一场文字会议，也让没有 Agent 的人从浏览器加入。模型与执行能力来自参与者已有的 Agent；NokNok 提供通信、邀请与会议空间。

主张的核心是“即时收发，连续追问”：用户给出目标与授权，Agent 直接交换进展、追问细节、带回明确结论。产品应让人看得见发生了什么，并保留决定与介入的入口。

## 用户与首个成功时刻

首要用户是已经使用 Agent 工作、又需要与他人协作的人：产品、设计、工程、研究与小团队负责人。第二类用户是被邀请的协作者，他们可能没有 Agent，也不需要为了补一句验收要求而先安装工具。

首个成功时刻：A 让自己的 Agent 联系 B 的 Agent；B 的 Agent 带着自己获准使用的上下文给出事实与证据，回答一个影响下一步判断的追问；A 收到“完成了什么、还缺什么、谁负责”的可用结果。用户不必复制两边的整段对话。

第二个成功时刻：A 创建会议并交付邀请链接，B 将链接交给当前会话里的 Agent，第三位协作者直接用浏览器加入，最终形成共同确认的决定与待办。

## 四个产品支柱与当前可用表述

| 支柱 | 面向用户的表达 | 当前证据与发布边界 |
| --- | --- | --- |
| Agent 即时沟通 | 消息实时传递，进展直接问，细节接着聊。 | 授权联系人、定向邀请、消息与会议流程已实现。主动唤醒还依赖接收方宿主支持原生 MCP Events、独立授权与真实接入验收；不能写成任意 Agent 已经支持自动唤醒。 |
| Agent 与人一起开会 | 一个链接，Agent 和人都能加入。 | 已实现多人文字会议、浏览器人工发言与人/Agent 标签。当前不提供音视频通话；“会议”在本产品中指有目标、有主持者的文字协作。 |
| 自部署 | 把通信服务放在你选择的环境。 | 基础会议与托管模式都有自部署入口。所有参与端须能访问同一服务；云端宿主通常需要可访问的 HTTPS 入口。切换部署要建立该部署自己的身份与授权。 |
| 源码公开与开放计划 | 查看源码，理解它如何连接。 | 仓库可查看；当前 `package.json` 为 `UNLICENSED`，不能直接宣传已经采用开源许可。正式使用“开源”前需明确并添加许可证。 |

推荐首屏辅助文案：

> 即时沟通，进展直接问，细节接着聊。把各自的助手，带进同一场对话。

“即时”描述消息沟通能力：服务新增消息后会立即结束等待中的长轮询，CLI 与浏览器持续接收更新，参见 [`src/meetings.mjs`](../src/meetings.mjs)、[`src/meeting-client.mjs`](../src/meeting-client.mjs) 与 [`web/meeting.js`](../web/meeting.js)。已接入且正在接收消息的参与者可持续交换消息；模型生成回复的耗时、宿主调度与网络状况仍会影响回应速度。文案不承诺“秒回”“零延迟”或任意离线 Agent 都会自动醒来。

主动唤醒的准确表达：

> 支持原生事件的宿主，可在用户授权后接收新邀请。真实 dot / Grokbot 的自动加入与回复仍待接入验证。

不要在主标题旁放“所有 Agent 随时在线”“100% 自动接听”“已支持 dot × Grokbot”等已完成式标识。演示角色名不是兼容性认证。

## 关于“私有部署”的判断

可以称为“支持自部署”，因为服务与数据目录由使用者自己运行，客户端可以指向该服务。这里的“私有”指部署与运营控制权，不保证只有内网可达，也不自动提供对运营者保密的端到端加密。

| 场景 | 网络要求 | 对主动唤醒的影响 |
| --- | --- | --- |
| 所有 Agent 和人都在同一可达内网，使用普通邀请 | 参与端可访问同一服务地址；实际配置以部署说明为准 | 可以做当前会话内的邀请与收发，无须证明后台唤醒。 |
| 云端 dot / 其他云端 Agent 访问自部署服务 | 服务入口必须从该云端执行环境可访问，通常使用公网 HTTPS | 还需宿主支持 Events、接受认证配置，并能完成回调验证与实际执行。公网可达只是前提之一。 |
| 希望服务只在内网、同时唤醒公网云端宿主 | 需先验证宿主是否有受支持的网络接入路径 | 当前实现不提供隧道、内网代理或任意网络转发，不能承诺直接可用。 |

更换机器但保持同一个 origin，与更换整个服务空间不是同一件事。托管数据库绑定 origin；另一部署有独立身份、授权与数据目录。网站可以写“选择自己的部署”，不应写“改一下服务器地址，联系人自动全部迁移”。

当前原生 Events 回调只接受解析到公网 IP 的 HTTPS 地址；即使服务和客户端都在内网，也不能据此承诺纯内网后台唤醒。

完整条件放入部署入口与 FAQ，首页以“你选择服务部署在哪里”表达价值即可。

## 网站信息架构

首页围绕一次真实协作展开，避免把协议名作为主卖点。

1. **首屏：让你的 Agent，找到他的 Agent。** 主标题说明“你的 / 他的”连接关系，副标题突出即时沟通与连续追问。一段用途说明、一个可读的对话示例；主按钮“看协作演示”，次按钮“了解如何接入”。用“研发预览”明确当前阶段。
2. **能力概览。** 即时沟通、多人文字会议、自部署、源码公开。将唤醒条件紧邻对应功能；许可证状态紧邻源码入口。
3. **演示：一条发布任务，两次协作。** 提供 Case 01“同步进展，追问关键细节”和 Case 02“邀请大家，做最后一次对齐”的可切换分镜。录制完成后在同一区域嵌入视频；当前标识“演示脚本 / 视频待录制”，不放假的播放成功反馈。
4. **参与方式：带上 Agent，或直接加入。** 用三步说明：发起目标 → 分享邀请 → 形成决定；强调没有 Agent 的人可用浏览器发言。
5. **部署与边界。** 简短网络示意和“了解自部署”入口；说明原生事件与当前会话邀请的区别。
6. **FAQ 与下一步。** 能否唤醒任何 Agent、是否支持真人、是否需要公网、源码许可、当前可以体验到哪一步。末尾继续导向文档与仓库。

推荐 CTA：

| 文案 | 去向 / 行为 | 启用条件 |
| --- | --- | --- |
| 看协作演示 | 滚动到演示区域 | 立即可用；未录制时显示分镜说明。 |
| 查看源码 | GitHub 仓库 | 立即可用；不暗示已获开源许可。 |
| 了解自部署 | 部署文档 | 立即可用；目标文档保留当前测试阶段。 |
| 查看产品说明 | 本文或站内等价说明 | 立即可用。 |
| 开始使用 / 申请内测 | 将来的经过验收入口 | 完成 E2EE 与部署/宿主验收后再启用；当前不放空链接或模拟表单。 |

## 视频承接设计

视频主题建议为 **“周五发布前的最后一次对齐”**。它从同一个具体问题推进：邀请参会体验做到了哪一步，发布前还要核对什么。先让两个 Agent 收集事实和追问，再把需要共同决定的内容带进群聊，最后让没有 Agent 的同事补上一个验收条件。

视频应展示可判断的产物：一条关键澄清、一次真人补充、一份有责任人的发布前清单。两段案例既各自完整，也让观众理解为什么要从直接联系升级为多人会议。完整提示词与镜头表见 [演示脚本](demo-script.md)。

录制完成前使用清楚标识的示意对话。录制完成后保留章节入口、字幕与文字摘要，让不能播放视频的读者仍能理解产品。播放器不自动有声播放；视频地址缺失时不出现可点击的空播放按钮。

官网可以公开介绍研发中的产品；真实用户内测是否开放是另一个决策。目前仅适合合成内容的受限联调，不能因页面做好而开启真实用户数据处理。

## 本次设计的验收标准

- 读者能在首屏回答：这是连接已有 Agent 的即时通信产品，能减少人与人之间的复制传话。
- 两段案例覆盖直接联系、关键追问、多 Agent 参会与无 Agent 人类参与，并有明确输出。
- 任何示意对话、演示状态和未录制视频都有可见标识，不作为真实集成证据。
- 主动唤醒与人工转交链接分开说明；公开支持列表只包含通过真实宿主验收的组合。
- 网站提供有效文档与源码入口，没有伪造的客户、数字、视频或无法提交的表单。
- 小屏可读、键盘可操作、焦点可见；动画尊重减少动态效果设置。
- “自部署”说明覆盖网络可达、云端宿主、独立身份空间；“源码公开”与开源许可证不混用。
- 现有 `/meeting` 邀请与参会流程仍可用；营销页不引导用户从无邀请页面创建不存在的网页会议。
- 上线前 E2EE、真实宿主唤醒与许可证决策仍有明确责任与验证入口，不能由营销文案替代。

## 视觉方向

以“两个助手之间的一次敲门”为页面的辨识元素：错位的个人助手标记与对话便笺展示通信关系，低饱和背景将重点留给具体对话。首页采用非对称首屏、三列能力、场景选择与对话预览、真人参与示意和部署说明。
